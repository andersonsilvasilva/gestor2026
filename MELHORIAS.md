# Checklist de Melhorias — Gestor

Levantamento inicial feito a partir de leitura do código (models, controllers, rotas, migrations, config). Marque os itens conforme forem resolvidos.

## 🔴 Bugs que quebram funcionalidade (corrigir primeiro)

- [x] **Evento apagado era destruído para sempre, sem chance de recuperação** — `app/Models/eventos.php` tinha `use SoftDeletes;` comentado mesmo a migration já criar a coluna `deleted_at`. Descoberto escrevendo teste automatizado. Reativado + adicionado cast `datetime` em `start`/`end` (também ausente). Como duas queries usavam `DB::table('eventos')` cru (não passam pelo Eloquent, não filtram soft-delete sozinhas), adicionei `whereNull('deleted_at')` manualmente em `AgendaController::getEvents` e `DashboardController::buildChartData`, e `AND eventos.deleted_at IS NULL` nas 4 queries SQL dos relatórios Jasper (que rodam direto via JDBC, fora do Laravel) — sem isso, atendimentos "apagados" voltariam a aparecer no calendário, no dashboard e em relatórios oficiais assim que alguém excluísse um evento.
- [x] **Schema de `clients` desalinhado da migration** — a tabela real (importada da produção) tem `cpf`/`estado_civil` que a migration original nunca criava, e não tem mais `raca`/`complemento`/`last_atendimento` que a migration cria — além de quase todas as colunas serem `NOT NULL` na migration mas `NULL` de fato em produção. Descoberto ao tentar escrever teste para Clientes contra um banco criado do zero pelas migrations. Corrigido com 3 migrations novas (`add_cpf_and_estado_civil...`, `remove_obsolete_columns...`, `align_clients_table_with_production_schema` — essa última via SQL bruto `MODIFY COLUMN`, pois o projeto não tem `doctrine/dbal` instalado para usar `Schema::change()`). Aplicadas de verdade no banco de testes; marcadas como já aplicadas no banco de desenvolvimento (que já reflete esse estado, vindo do dump de produção).
- [x] **`Department` também apagava para sempre** — mesmo bug do `eventos`: `use SoftDeletes;` faltando no model mesmo a migration criando `deleted_at`. Corrigido.
- [x] **`ProcedimentoControl::deleteProcedimentoConfirm` não verificava os IDs protegidos (1 e 2)** — só a tela de confirmação (`deleteProcedimento`, GET) checava o bloqueio; a ação que efetivamente apaga (POST) não. Um POST direto ao endpoint apagava um procedimento "travado" mesmo sem passar pela tela com o cadeado. Corrigido adicionando a mesma checagem que `updateProcedimento` já tinha.
- [x] **`Procediment` apagava para sempre, sem chance de recuperação** — diferente de `eventos`/`Department`, a tabela real `procediments` em produção **nunca teve coluna `deleted_at`** e o model nunca usou `SoftDeletes`. Descoberto no primeiro deploy em produção: um procedimento de teste (id 12, "Biomagnetismo") foi apagado por engano durante o teste manual pós-deploy e precisou ser recriado manualmente via `INSERT` no phpMyAdmin. Corrigido com o mesmo padrão já usado em Clientes: migration `add_deleted_at_to_procediments_table`, `SoftDeletes` no model, `ProcedimentoControl::restoreProcedimento` (POST `/procedimento/restore/{id}`), botão Restaurar na listagem para linhas apagadas. Os relatórios Jasper só fazem `JOIN` em `procediments` pelo FK do evento (não listam procedimentos ativos), então não precisaram de ajuste — diferente do caso de `eventos`. Testado via HTTP real (soft delete + restore).
- [ ] **7 pares de clientes com o mesmo CPF válido, aparentando ser o mesmo paciente cadastrado duas vezes** (nome/data de nascimento batendo, CNS com 1 dígito de diferença) — descoberto ao tentar aplicar um índice único em `clients.cpf` (ver migration `make_cns_nullable_and_cpf_unique_on_clients`), que por isso **não** adiciona a constraint no banco, só valida na aplicação daqui pra frente. Precisa de revisão humana caso a caso: confirmar se é a mesma pessoa e, se for, mesclar o histórico de atendimentos (`eventos`) num único cadastro antes de poder apagar o duplicado e aplicar a constraint de verdade. Lista de CPFs afetados foi levantada em sessão (não incluída aqui por ter nome de paciente) — rodar a mesma query de novo se precisar: `clients` agrupado por `cpf` com `count > 1`.
- [ ] **Criar colaborador quebra com erro de SQL se "Observações" ficar em branco** — `user_details.comentario` é `NOT NULL` sem default na migration, mas o campo no formulário (`add-rh-user.blade.php`) não é obrigatório e nem validado em `RhUserController::createRhColaborator`. O middleware padrão do Laravel (`ConvertEmptyStringsToNull`) converte o campo vazio pra `null`, e o insert falha com `Column 'comentario' cannot be null`. Descoberto escrevendo teste para a mudança de CNS→CPF (ver item de identificação SUS). `salario`/`admission_date` têm o mesmo risco (`NOT NULL` sem validação de obrigatoriedade) se algum dia o formulário permitir deixá-los em branco. Precisa de migration tornando as 3 colunas nullable, igual já foi feito em `clients`.
- [x] **SUS extinguiu o CNS como identificador de controle, substituído pelo CPF** — CPF agora é obrigatório/único para clientes (`clients`) e colaboradores (`user_details`, que ganhou a coluna `cpf`, antes só tinha `cns`); CNS virou opcional em ambos (campo mantido pra quem já tem o cartão). Ajustado: `ContaRequest`, `ClienteController::updateCliente`, `RhUserController` (create/update), telas de cliente e colaborador, `AgendaController`/`ListarAtender` (identificador "codigo" da agenda agora é o CPF). Nos relatórios oficiais AVEIANM, BPA-I e sub-BPA (Jasper), a coluna de dado trocou de CNS pro CPF; no AVEIANM o rótulo da coluna também mudou pra "CPF", mas no BPA-I o rótulo "CNS" está desenhado dentro da imagem do cabeçalho oficial do SUS (`cabecallho_bpa.png`/`body_bpa.png`) e não foi alterado — decisão explícita do usuário de mostrar CPF sob o rótulo "CNS" por ora, até haver um cabeçalho oficial atualizado. `ficha_acolhimento.jrxml` também usa CNS mas não está roteada/em uso hoje, não foi tocada.

- [x] **Relacionamentos Eloquent sem `return`** — `app/Models/User.php`, `app/Models/Client.php`, `app/Models/Procediment.php`, `app/Models/Department.php`, `app/Models/eventos.php`. Corrigido: adicionado `return` e trocado `belongsToMany` (que assumia pivot table inexistente) por `belongsTo`/`hasMany` de acordo com as FKs reais do schema (`user_id`, `client_id`, `procediments_id`, `department_id`). Validado via tinker contra o banco local.
- [x] **`AgendaController::mostraDados`** — corrigido para usar as relações `Procediment_eventos`/`user_eventos` (agora funcionais) em vez de tratar as FKs inteiras como objetos. Retorno do JSON também corrigido (estava passando parâmetros errados para `response()->json()`).
- [x] **`AdminController`** — removido (código morto, não roteado, referenciava models inexistentes). Indicadores de admin já são cobertos pelo `DashboardController`.
- [x] **`BookController`** — removido junto com `app/Imports/BookImport.php` (dependia de pacote não instalado, não roteado, view inexistente). Import de planilha vira item de feature futura, se necessário.
- [x] **`JasperController::console()`** — método removido (caminho absoluto Windows hardcoded, só usado para teste manual). Resto da classe mantido (usado por `ControllerReport`).
- [x] Validação com typo em `AgendaController::store`: `max255` → `max:255`.
- [x] **XSS armazenado em potencial** nos gráficos do dashboard — `DashboardController` agora monta arrays PHP normais (em vez de strings pré-formatadas com aspas manuais), e `home.blade.php` usa `@json()` em vez de `{!! !!}` para os labels e dados dos gráficos Chart.js.

## 🟠 Segurança

- [x] **Autorização por papel implementada para Departamentos/Procedimentos/Colaboradores/Configurações/Gestão de Usuários** — Gates `manage-catalog` (admin + RT) e `view-all-data` (admin + RT + secretaria) em `AppServiceProvider`, aplicados via middleware `can:` nas rotas (`routes/web.php`). Testado via HTTP real para os 4 papéis (admin/rt/sec/rh). O Gate `admin` pré-existente tinha um bug (usava `auth()->user()` global em vez do parâmetro `$user`) — corrigido. Os `Auth::user()->can('admin')` comentados nos controllers de Clientes/Agenda/Perfil continuam pendentes (ver item logo abaixo — RT/Secretaria já tratados, falta granularidade fina se necessário).
- [x] **Operações destrutivas via GET** — convertidas para `POST` com `@csrf`: exclusão de cliente/colaborador/departamento/procedimento/evento e restauração de cliente. As telas de confirmação (que só exibem a pergunta "tem certeza?") continuam em `GET`, só a ação que efetivamente muda dado virou `POST`. Testado via HTTP real (GET agora retorna 405, POST com CSRF funciona) para os 5 fluxos.
- [x] Gates centralizados em `AppServiceProvider` (`admin`, `manage-catalog`, `view-all-data`) cobrindo as telas administrativas. `app/Policies` continua não existindo — se o modelo de permissões crescer mais (ex: por recurso específico, não só por tela), vale migrar para Policies de verdade.
- [x] **Política de senha unificada** — havia na verdade 3 fluxos fracos (Fortify `reset-password`/`user/password` e `ProfileController`) contra 1 forte (`ConfirmAccountController`). Unificado via `Password::defaults()` (min 8, maiúscula+minúscula+número, sem máximo artificial) em `AppServiceProvider`, usado pelo `passwordRules()` do Fortify (`app/Actions/Fortify/PasswordValidationRules.php`) e agora também por `ConfirmAccountController` e `ProfileController` (que reaproveitam o mesmo trait). `max:16` removido — testado aceitando senha de 20+ caracteres. Verificado via HTTP real.
- [ ] Credenciais de produção (DB, SMTP) estão em texto puro no `.env` do projeto (esperado para Laravel, mas confirme que backups/`.env.production` nunca vão para controle de versão ou para fora da máquina local).
- [ ] Sem `EnsureEmailIsVerified` aplicado nas rotas, mesmo com `Features::emailVerification()` habilitado no Fortify — o recurso está ligado mas não é de fato exigido em nenhum lugar.
